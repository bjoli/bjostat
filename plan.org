* bjostat: the plan

What is done, and what comes next. A table is an Arrow record batch whose
schema is known when the program runs. Work on it is one API: Bjolang's
~loop~, with collectors for what it makes, which Bjolang compiles to vector
code where it can. Beside the loop are the operations on whole tables that
are not loops, and statistics, as R has them.

** Done: tables (bjostat table)

- A ~Table~ is an Arrow ~RecordBatch~. Its schema is read at run time.
- A column is taken out by name and type, and the type is checked once:
  ~(doubles t "price")~ is a ~(Column double)~ or an ~Err~ that names the
  columns the table has.
- A typed column gives its values as a span. The aggregates use
  ~TensorPrimitives~ when the column has no nulls.
- Arrow IPC files in and out. A file of several batches is read as one
  table, each column in one piece.
- Sorted (~table-sort~) and joined (~inner-join~ and the others), and
  columns of dates and timestamps: see "Done: what R has, the first part".

** Done: CSV (bjostat csv)

- ~read-csv~ and ~csv->table~ read through ~(text csv)~. The types are
  guessed from the first rows, or given by name with ~#:types~. An empty
  field is a null.
- The glue parses each field from its UTF-8 bytes into arrays from the
  shared pools, and makes Arrow buffers once. 1 000 000 rows of five columns
  in 175 ms; ~(text csv)~ alone takes 95 ms.
- Faster still would be fields as spans of the reader's chunk: ~(text csv)~
  now makes a string of each field and an array of each row, which is most
  of what it allocates, and read-csv only copies the bytes on.
- Dates, dates and times, and instants (ISO 8601) are guessed too.
- Other null markers, as R's ~NA~, by ~#:nulls~; booleans are guessed.
- Not yet: columns that are skipped.

** Done: the function layer of queries (bjostat query)

- ~(column-as t name)~ gives ~(Cells %a)~ at the type its use gives; the
  check of the Arrow type against ~%a~ is in the glue, by ~typeof(T)~.
- A row spec is ~col~ and ~both~, as the applicative of Laurent Mazare's
  OCaml ~dataframe~: ~(both (col "price") (col "qty"))~ is a
  ~(Row (Tuple double long))~, checked against the schema before a row is
  read.
- ~where-rows~, ~count-rows~ and ~create-column~ take a spec and a
  function. Nulls are as in SQL. ~where-rows~ gathers the rows kept in the
  glue: fixed-width types by their width, strings, booleans, and runs of
  slices for the rest.

Measured on 1 000 000 rows, two columns read (bench/query.bjo):

| Loop                          | Time        | Against spans |
|-------------------------------+-------------+---------------|
| over the spans, by hand       | 0.38–0.50 ms | 1             |
| over cells, by hand           | 0.75–1.3 ms | 2–3           |
| ~count-rows~: closures, tuple | 5.8–6.7 ms  | 12–15         |
| ~where-rows~: count and gather | 7.4–8.9 ms |               |

So the macros write the loop over cells themselves, with the body in it,
and the function layer is for names known only at run time. A cell read
first made a span of the buffer each time; Arrow's own buffers are native
memory, so cells now pin them once and read through a pointer (1.8 to
1.3 ms in one run). A struct for cells gained nothing.

Cells are ~Iterable~, with an ~(Option %a)~ for each row, so a ~loop~ walks
columns side by side and the SQL rule is ~:when-let~:

#+BEGIN_SRC scheme
(loop (:for p* price) (:for q* qty)
      (:when-let (Some p) p*) (:when-let (Some q) q*)
      (:when (and (> p 250.0) (> q 20L)))
      (:acc (counting p)))
#+END_SRC

That loop takes 1.51 ms where the loop over cells by hand takes 1.44 ms, in
one run: an Option is a struct, and the null costs about 5%. So the macros
expand to this loop form, and a program can write it too. ~skip-nulls~ walks
only the values, as Julia's ~skipmissing~, for one column on its own.

** Done: collectors, for loops over cells

The columns are found before the loop, with ~column-as~ in a ~def~ where an
~Err~ can propagate, and the loop does the rest. There is no query form of
its own: ~where~ is a ~:when~, ~create~ a ~:let~, and ~aggregate~ an ~:acc~,
so a pipeline is one loop and makes no table between its steps.

- ~(selecting t row)~: the table of the rows kept. 4.4 ms on 1 000 000 rows,
  against 8.6 ms for ~where-rows~.
- ~(column-building x)~ and ~(column-building/option o)~: a column, with a
  null at each ~None~; ~table-with~ adds it. 3.5 ms; the arrays come from the
  shared pool, as in the CSV reader, and before that it took 13.4 ms.
- ~(grouping c (Tuple key x))~: a map from each key to what the collector
  ~c~ makes of its values. ~(pairing c d)~ is two collectors at once, so
  ~(grouping (pairing summing counting) ...)~ gives two aggregates of each
  group. ~map->table~ makes a table of a map. A collector over a collector
  needed nothing new in Bjolang: the implementation names the associated
  types of the inner one, as ~(assoc Collector acc %c)~.

~grouping~ took 52 ms by four string keys and 12 ms by forty long keys. The
long keys allocated 32 bytes a row: the dictionary of ~grouping~'s
conditional implementation was built at each step. Bjolang now builds such
a dictionary once, and splices the methods of a library's implementations
into the loop that calls them, so the loop has no dictionary at all: 5.6 ms
and nothing allocated by long keys, 46 ms by string keys.

** Done: groups by number

~(group-of! groups key)~ gives each key a number, in the order first seen,
and the ~-by~ collectors keep an array by that number: ~summing-by~,
~counting-by~, ~min-by~, ~max-by~, ~mean-by~. Each takes the groups, so that
its column has a row for each group: 0 for a sum or a count where its rows
did not reach a group, a null for the others. ~groups->table~ makes the table
of the keys and those columns. Each aggregate is its own ~:acc~ and can have
its own ~#:when~.

Measured on 1 000 000 rows:

| Groups                                  | String keys | Long keys |
|-----------------------------------------+-------------+-----------|
| ~grouping summing~                      | 48 ms       | 5.6 ms    |
| ~summing-by~                            | 34 ms       | 5.8 ms    |
| ~grouping (pairing summing counting)~   |             | 5.8 ms    |
| ~summing-by~ and ~counting-by~          |             | 6.9 ms    |

The key is hashed once a row instead of twice, which is most of the cost by
strings. By longs the two are level, and a second aggregate costs about 1 ns
a row as a ~-by~, which reads and writes a ~List~, and 0.2 ns in a ~pairing~,
whose two sums are in the map's value.

A string cell was copied out of Arrow and checked at each row. Now the
column's strings are one Bjolang string, checked once, and a cell is a slice
of it (~Utf8String.SliceBytes~ in BjoString, which refuses an end in the
middle of a character, so no slice is invalid UTF-8). That took grouping by
strings from 48 to 36 ms, and ~summing-by~ from 34 to 26 ms. It allocates as
much as before: a slice is a small object, as big as the copy of a short
string was. Codes for the strings of a column, found once from the bytes, so
that a row needs no string at all, are next.

** Measured against Polars

The same file of 1 000 000 rows (bench/compare/make_data.py), the same
operations and the same results, in bench/compare.bjo and
bench/compare/polars_bench.py. Polars 2.1.0, eager, the median of 20 runs.
bjostat with Bjolang's vector loops (measured; first numbers in brackets):

| Operation                    | bjostat            | Polars, 1 thread | Polars, 24 threads |
|------------------------------+--------------------+------------------+--------------------|
| read CSV (26 MB)             | 187 ms (182)       | 72.9 ms          | 19.0 ms            |
| filter, kept rows            | 4.37 ms (11.7)     | 4.03 ms          | 2.61 ms            |
| new column                   | 1.00 ms (6.15)     | 0.62 ms          | 0.72 ms            |
| group by string, sum         | 27.9 ms (29.9)     | 8.31 ms          | 2.51 ms            |
| group by long, sum and count | 6.74 ms (6.14)     | 7.27 ms          | 1.68 ms            |

The loops of bjostat run on one core. The copy of the kept rows of a filter
runs on one thread for each column, because most of its time is to get new
memory, which the threads get at the same time. The new column varies
between processes, from 0.99 to 2.84 ms; it is 8 MB of new memory each
time.

The filter took 20.8 ms at first. Of that:
- The test of random prices: the loop alone took 5.9 ms, and 1.7 ms with a
  test that is always true. ~(and a b)~ was a jump on ~a~, mispredicted half
  the time. Bjolang now writes ~and~ and ~or~ of cheap comparisons as C#'s
  ~&~ and ~|~, both sides evaluated, no jump (Simplify.fs): 3.5 ms.
- The ~:when~ is a jump too. A ~selecting-if~ collector wrote every row
  and counted the kept ones, with no jump: 1.2 ms less. It was removed when
  Bjolang's vector loops made ~:when~ and ~selecting~ faster than it: the
  loop alone takes 1.37 ms, and one API is enough.
- The copy of the kept rows: validity was read through ~IsValid~, an
  interface call a row, and every array was zeroed before it was written.
  The bitmap is read directly now, with no jump on each bit, and the arrays
  are not zeroed; a short string is copied as 16 bytes at once. A copy into
  an array that was used before takes 0.15 ms for 250 000 longs, and a new
  array of 2 MB costs 0.85 ms more to get its pages from the operating
  system, so the columns are copied on several threads. Memory of the C
  allocator would not cost that, but a span of it is not seen by the
  garbage collector, which could free it while a loop reads it.
- The loop alone, with ~:when~ and ~selecting~, became a vector loop: 4.1 ms
  became 1.37 ms.

The new column took 5.7 ms. Ways to make it faster were measured in paired
rounds (--compare-within); of them, only the faster builder is kept, as the
next section says:
- The growing builder copied the column as it grew and once more at the
  end. ~column-building/sized~ writes into the buffer the column ends in:
  3.9 ms.
- ~column-map~ and ~column-map2~ deal with the nulls once, before the loop,
  and splice the function they are given: 2.7 ms.
- Kernels on whole columns, ~column*~ and the others, by TensorPrimitives:
  1.9 ms. The multiplication takes 0.7–1.0 ms, as Polars's 0.62. The cast of
  longs to doubles takes the rest: neither ConvertChecked nor
  ConvertTruncating is vectorized for it. A kernel of a double and a long
  column would leave it out.
- A loop of plain values over spans with a sized builder takes 1.2–2.2 ms:
  about what code a row can do in .NET, which does not vectorize loops.
- Bjolang's vector loops then made the loop with ~column-building/option~
  1.0 ms: 4.2 ms with the same code in scalar loops.

** Decided: one API, the loop

The kernels, ~column-map~ and the sized builders made three ways to make a
column: one fast, one comfortable and one general. A program should have one
way, and it is the loop. A Python library has a second API, arithmetic on
whole columns, because a Python loop is 50 times slower than a Bjolang one.
Bjolang's loops are compiled, as Julia's are; what they lack is vector code.

So:
1. Done: bjostat keeps the loop and its collectors, and nothing beside them
   for the same work. The kernels, ~column-map~ and the sized builders are
   gone. ~column-building~ keeps a column of numbers as bytes, so that the
   array it grew in is the buffer Arrow is given, with no copy at the end:
   4.2 ms where it took 6.5, in three pairs of runs, as fast as the sized
   builder, without being told the size.
2. Done, on the vectorise branches of Bjolang and bjostat: Bjolang
   vectorizes simple loops: maps over ranges, arrays and spans; loops over a
   library's values through the trait ~Contiguous~, with null bitmaps as
   masks; counts and integer sums under ~:when~; and filters into a
   ~BlockCollector~, the kept lanes put next to each other. bjostat
   implements ~Contiguous~ for the cells of a column of numbers, and
   ~BlockCollector~ for ~column-building~, ~column-building/option~ and
   ~selecting~. The design and its status are in Bjolang's
   Docs/Vectorisation-design.org. ~selecting-if~, a second way to filter
   with no jump, was slower than the vector loop and is gone.

Arithmetic on columns, as ~(* price qty)~ of two columns, is not in the
plan: ~*~ is ~INumber~'s, which a column cannot be, and each step would make
a column, which a vectorized loop over all its columns does not.

Next, besides: codes for strings (group by string, joins by string), CSV
from the bytes, and loops over rows split across cores.

** Done: what R has, the first part

The tables, the CSV, the loops and the collectors are the representation.
What R adds for work on data is a set of operations on tables, column types
and statistics. Done so far:

- *Sort:* ~(table-sort t [(ascending "region") (descending "price")])~, as
  R's ~order~: stable, a null last in both directions, a NaN after every
  number, strings by code point. Each key is one stable pass, from the last
  key to the first: a radix sort of 64-bit keys whose unsigned order is the
  order of the values, and a string key is first the rank of each string
  among the distinct ones.
- *Joins:* ~inner-join~, ~left-join~, ~semi-join~ and ~anti-join~, as
  dplyr's: the left rows in their order, two nulls equal keys, ~.x~ and
  ~.y~ on names both tables have. The right rows go in a hash table by the
  hash of their keys, with the rows of a hash in a chain in their order.
- *Dates and timestamps:* columns of Arrow's Date32 (days since 1970) and
  timestamps in microseconds, with or without a time zone. ~date-cells~,
  ~datetime-cells~ and ~instant-cells~ give their cells as ~Date~,
  ~DateTime~ and ~Instant~ of ~(std datetime)~, through its
  ~unix-days->date~ and ~unix-microseconds->instant~; ~dates-building~ and
  the others make such columns. No reflection on ~(std datetime)~'s types,
  so a program built ahead of time works the same. CSV reads ISO 8601.
- *Statistics* in ~(bjostat stats)~, as collectors of doubles: ~mean~,
  ~variance~, ~standard-deviation~, ~covariance~, ~correlation~, ~median~,
  ~quantile~, ~quantiles~ and ~summarizing~, as R gives them, and
  ~table-summary~ of a whole table. The one-pass statistics sum the
  differences from the first value; a quantile is found by selection, not
  by a sort (60 ms became 16.5).
- *Reshaping:* ~table-distinct~ (dplyr's ~distinct~ with ~.keep_all~),
  ~table-append~ (~bind_rows~: columns by name, nulls where a table has
  none), ~pivot-longer~ and ~pivot-wider~ (tidyr's). Rows of equal keys are
  found with the hashes and comparisons of the joins. A column is put after
  another by a copy of its buffers, not of each cell as Arrow's
  ~ArrowArrayConcatenator~ does: an append of 1M rows to 1M rows became
  21 ms from 75, and a pivot to longer rows 22 ms from 88.
- *Bools:* Arrow's Boolean is ~Bool~ in the schema, with cells of ~bool~;
  CSV reads ~true~ and ~false~ (and ~TRUE~, ~True~); ~table-summary~ counts a
  bool as 0 or 1, so its mean is the share of trues.
- *Categories:* ~table-categorize~ makes a column of strings an Arrow
  dictionary of int codes and string levels, as R's ~factor~: the levels
  sorted, or given, and a string not in them an Err (R makes it NA). Its
  cells are strings, so a loop over strings works on it unchanged;
  ~category-codes~ gives the codes as ~(Cells int)~ and ~category-groups~
  the groups of the levels, so that a group-by has no hash. A sort is in the
  order of the levels; a join on one category key matches codes through an
  array; an append of other levels has the levels of both, in order, as R's
  ~rbind~ of factors. A null under a join key now hashes the same whatever
  value Arrow keeps under it, which a left join could make differ before.
  The distinct strings of a column are found by open addressing over its
  bytes, which made a sort by a string 72 ms from 110.
- *Counts:* ~table-count~ (dplyr's ~count~: a row for each distinct key,
  sorted, a null a value) and ~table-crosstab~ (R's ~table(x, y)~: a column
  of counts for each value of the second key, 0 for a pair no row has, rows
  with a null left out). Rows of equal keys are now found without a hash of
  each row: each key column gives its values ids (a category its codes, a
  string the open addressing of its bytes, an integer its distance from the
  least), and the ids of the columns are put together as the digits of one
  number, numbered again from 0 after each column. When each row is a group
  of its own, the other columns are not read. A count by a string and a
  long became 15 ms from 60, a distinct by them 14.5 ms from 60, and a pivot
  to wider rows 75 ms from 151.
- *Distributions:* ~(bjostat distributions)~ has the density, the
  distribution function, the quantile function and samples of the normal,
  t, chi-squared, F, binomial and Poisson distributions, with ~#:lower?~
  for upper tails as R's ~lower.tail~. The functions are made of the log
  gamma function and the regularized incomplete gamma and beta functions,
  with Stirling's series where large terms would cancel; a quantile is
  Newton's method on the logarithm of the tail, kept in a bracket. Checked
  against mpmath: below 1e-12 relative almost everywhere. The samples are
  exact methods on ~(std random)~'s seeded sources: Box and Muller,
  Marsaglia and Tsang, Hörmann's PTRS, and beta splits of the binomial.
- *Linear models:* ~(bjostat models)~: ~linear-model~,
  ~linear-model/origin~ and ~simple-linear-model~ are collectors that fit
  R's ~lm~ in one pass, by Givens rotations into the R of a QR
  decomposition and Q'y; the residual sum of squares is what is left of y.
  The model has R's ~summary.lm~: estimates, standard errors, t values,
  p-values, sigma, R², adjusted R² and F, printed as R prints them, and a
  table as broom's ~tidy~. Checked against R's ~cars~ and against mpmath
  at 50 digits to 1e-12; on x and x² near 10 000 the estimates are within
  1.1e-8, where the normal equations in doubles are within 6e-3. Measured
  on 1M rows: 17.7 ms for one predictor, 62.6 ms for three, which allocate
  a Vec for each row.
- *Generalized linear models:* ~logistic-model~ and ~poisson-model~, R's
  ~glm~ of the binomial and Poisson families with the logit and the log, by
  iteratively reweighted least squares with R's start and stop; each step
  is the Givens QR of the weighted rows, which the collector keeps.
  Estimates, standard errors, z values, p-values, deviances and AIC agree
  with R's mtcars ~am ~ wt~ and with Newton's method at 50 digits to 1e-7.
  The standard errors are of the weights at the estimates, one pass more;
  R's are of the weights of the last step, a step behind, and differ by
  about 1e-4 (R prints 1.436 for 1.43653).
- *Intervals and categories in models:* ~model-intervals~ (R's ~confint~)
  and ~glm-intervals~ (Wald's, R's ~confint.default~); ~indicators~ and
  ~indicator-names~ make a category the predictors of R's treatment
  contrasts.
- *Tests:* ~(bjostat hypothesis)~: one-sample, paired, Welch and pooled
  t-tests as collectors, with the p-values of the three alternatives and
  the interval of any level, and the chi-squared test of a crosstab with
  Yates's correction of 2 × 2, as R's. Checked against R's ~sleep~ and
  against mpmath at 50 digits, to 1e-11.
- *Rows after the fit:* a ~LinearModel~ keeps (X'X)⁻¹, R's ~cov.unscaled~,
  so a second loop over the rows gives R's residuals, ~hatvalues~,
  ~rstandard~ and the intervals of ~predict~, of the mean and of a new
  response. Checked against R's ~cars~ to 1e-12.
- *Columns and categories, typed:* the macro ~columns~ of ~(bjostat
  columns)~ takes several columns at the types written, as a ~def*~ of
  ~column-as~ with ~:propagate~; ~with-categories~ makes any model take the
  codes of categories as predictors of their indicators, with R's names.
  Not a formula macro as R's ~y ~ x + z~: the types of its columns would be
  checked when the program runs, or written in the formula, and the loop
  says each type and what a null does.
- *More tests:* the correlation test (R's ~cor.test~), Wilcoxon's rank-sum
  and signed-rank tests (exact, by counting the sums of subsets of the
  ranks, as R when there are fewer than 50 values and no ties, and of the
  normal approximation with R's corrections otherwise), Fisher's exact test
  of a 2 × 2 table, and ~model-anova~, R's ~anova~ of a linear model from
  the effects of its QR. Checked against the examples of R's help, whose
  exact p-values were counted again over every subset. The odds ratio of
  Fisher's test is the conditional estimate to 1e-12; R's ~uniroot~ gives
  it to 1e-6 (6.408309 for 6.4083197).
- *Nulls in loops:* ~skip-nulls~ gives the values of one column that are
  not null, and ~complete-rows~ the rows of 2, 3 or 4 columns where none
  is, as a Tuple, as R's ~complete.cases~. With nulls they are as fast as
  ~:when-let~; without them, 4.3 ms against 2.5 ms of a million rows, as
  ~:when-let~ then reads the cells as spans (bench/nulls.bjo).
- *Plots* are a package of their own, ~(bjostat plot)~ in the repository
  bjostat-plot: Vega-Lite specifications of tables, images by vl-convert,
  and the Palmer penguins of two R tutorials as an example, whose values
  agree with R's. The port added ~#:nulls~ to the CSV reader and kept the
  digits of small p-values in ~table->string~.

Of the one-thread columns, bjostat is the fastest at 9 of 25 and the
slowest at 4: the CSV, a group by a string, a join by a long, and a pivot
to longer rows. What the numbers do not say:
- dplyr has no row of its own where it uses base R (the statistics, the
  crosstab) or fread (the CSV).
- pandas reads the CSV in 30 ms with pyarrow at one thread, and in 86 ms
  when the process is pinned to one core: the read uses more than one core.
  Pinning the others is not fair either: .NET compiles and collects on
  threads of its own, and pinned bjostat read the CSV in 567 ms.
- pandas joins by ~id~ in 2 ms because both keys are sorted and unique,
  which it checks first; bjostat and Polars hash them.
- A distinct of rows that are all distinct is fast in bjostat because the
  ~id~ column alone makes each row a group, and then the other columns are
  not read.
- The summaries are not the same: R's has quartiles, pandas's the counts of
  strings, Polars's and bjostat's nulls and the min and max of strings.
- data.table's ~new column~ is a new table, ~c(.SD, ...)~, as the others
  make; its ~:=~ would change the table in place.
- R's medians are above its fastest runs by up to a factor of 4 where its
  garbage collector runs (new column: 44.6 ms, fastest 11.4).

The hash of a string key is made from its bytes for each row: a join by
strings is 82.5 ms, and one by a category of the same strings 12.0 ms. A
join by strings could find the distinct strings first, as a category does.
The one-pass statistics are sums of doubles, which Bjolang does not vectorize unless a program asks,
because the vector adds in another order.

** Next: the rest of what R has

First what the comparison with Polars, pandas and R taught, the parallel
loops before anything else, as they change the Collector trait:

1. *Parallel loops.* Polars on 24 threads is 3 to 10 times faster than
   every library on one, and bjostat has no way to use a second core. A
   prototype, bench/parallel.bjo, cuts a table into slices
   (~table-slice~, no copy), runs the same loop on each slice as a fiber
   (~spawn-thunk~ in a ~with-scope~), and adds the partial sums in the
   order of the slices. The sum of price × qty of 1M rows (measured): 2.49
   ms on one thread, 1.43 ms in 2 parts, 0.76 in 4, 0.48 in 8, 0.44 in 12
   and 0.54 in 24; from 8 parts on, memory is the limit.

   How it fits Bjolang's CML: the parts are fibers of the pool that runs
   every other fiber of the program, on real threads. So a program that
   already runs many fibers, as a server does, shares the cores with the
   parts instead of having more threads than cores; a scope waits for the
   parts and cancels them; fiber-trace sees them. ~spawn/thread~ is not
   needed: it makes a thread of 1 MB of stack for each call, which costs
   more than a part of a millisecond. The wait for the parts is
   ~by-colour~: ~promise-join/sync~ in ordinary code, ~(sync
   (promise-join p))~ in a bjoroutine, which must not park a thread of the
   pool. With ~promise-join/sync~ alone, the benchmark, which runs its
   bodies in fibers, hung.

   What is to decide:
   - *Combining.* A part gives the accumulator of its collectors, and two
     accumulators become one by a new method, ~collector-combine~, in a
     trait of its own beside Collector, so that a collector without it
     still works on one thread. Sums, counts, the moments (~moments-add~
     is already there), means, variances, correlations and a linear
     model (two R factors of a QR, stacked and rotated again) combine.
     ~selecting~, ~column-building~ and ~vecing~ combine by putting the
     parts one after the other. The median and quantiles combine by their
     values, or by a t-digest. ~folding~ does not, unless the program
     gives the combine.
   - *Groups.* ~group-of!~ writes one GroupIndex, which two threads cannot
     share. Each part needs an index of its own, and the combine numbers
     the groups of the second part again in the first. Groups of a
     category, ~category-groups~, are numbered before the loop, and
     combine by adding arrays.
   - *The same result on every machine.* A sum of doubles depends on its
     order. If the number of parts came from the number of cores, a mean
     would differ between machines. So the size of a part comes from the
     rows, as 64 000 of them, and the parts are combined in their order,
     whatever the number of threads that run them.
   - *How a program asks for it.* The loop stays the one API. A function
     over parts, ~(in-parts t (fun (u) (loop ...)))~ with the loop's
     collectors combined, needs no change in Bjolang; a ~:parallel~
     clause of the loop would be shorter and needs the compiler. Try the
     function first.
   - *What runs it.* Fibers of the pool, as the prototype. The copy of
     the kept columns of a filter runs on .NET's ~Parallel.For~
     (glue/Query.cs), outside Bjolang's scheduler; it should go through
     the same parts.
2. *Ids instead of hashes for strings and integers.* bjostat is the
   slowest of five at a group by a string (29.4 ms) and at a join by a
   long (136 ms, 137 MB), and slow at a join by a string (82.5 ms). Its
   counts and categories already give each key an id without a hash of
   each row: a count by a string takes 15.7 ms and a group by a category
   2.45 ms. Use the ids for ~group-of!~ of strings and for joins by
   strings, and for an integer key the distance from the least as an
   index, as the counts do, when the keys are dense enough. Check also
   whether both keys of a join are sorted and unique, as pandas does: its
   join by ~id~ takes 2 ms.
3. *CSV fields as spans.* bjostat reads the file in 189 ms, Polars in 73
   and data.table in 141: ~(text csv)~ makes a string of each field and an
   array of each row.
4. *A second file for the comparison,* of another shape: keys of many
   values, nulls in the numbers, more columns. One file says little:
   bjostat's distinct of rows is fast only because ~id~ makes each row
   distinct.
5. *Statistics:* a t-digest for quantiles in one pass with little memory.
6. *Parquet*.
7. *Nulls of dates and times.* ~skip-nulls~ and ~complete-rows~ take
   ~Cells~ only, not ~DateCells~, ~DateTimeCells~ or ~InstantCells~. A
   trait of a column with nulls (its length, its null count, whether a row
   is valid, the value at a row), with an implementation for each of the
   four, lets both be generic over it: ~(Tuple %a %b)~ where each is such a
   column, so that a date and a double go in one ~complete-rows~. Tests of
   dates, timestamps and a mixed tuple, and ~bench/nulls.bjo~ again to see
   that ~Cells~ is not slower.
   Also the number of each complete row, so that ~selecting~ can go with
   ~complete-rows~: a filter of rows now walks all of them with
   ~:when-let~, as examples/countries.bjo does.

Not from R: the recycling of short vectors, silent conversions between
types, NA that spreads through a sum unless the collector says so, and
operations on whole vectors as a second API.

** Found in Bjolang while writing this

Fixed in Bjolang, and the generic code is now in Bjolang, not in the glue:

- A generic ~import/extern~ did not take Bjolang's ~string~ for a .NET
  ~System.String~ parameter. Now it does, and the call converts it.
- A Bjolang function generic over ~(Column %a)~ was a C# method generic over
  ~T~ without Arrow's constraint ~where T : struct~, which C# refused. Now
  Bjolang finds the constraints and writes them as ~where~ clauses. A call at
  a type that breaks one is a Bjolang type error.
- A ~match~ on a ~Tuple~ of two Options cost 2.4 ms a million rows more
  than two nested matches. Now it costs 2% more, and a ~:let~ of a
  ~Tuple~ costs nothing (measured in paired rounds).

Still open, checked again on the vectorise branch:
- A column type that nothing decides is left as ~object~:
  ~(count-rows t (col "price") (fun (p) #t))~ compiles, and is then an Err
  at run time, "'price' is a column of double, not of Object". It should be
  a Bjolang error that asks for the type.
- The inferred ~where~ clauses are on functions only, not on type
  declarations: a Bjolang struct with a field ~(Column %a)~ is refused by C#,
  as Arrow's ~PrimitiveArray<T>~ needs ~where T : struct~. The glue's
  ~Cells<T>~ has no constraint for that reason.
- A module-level ~def~ that starts fibers which read the module's other
  values hangs: the fibers wait for the module to be set up (its static
  constructor in .NET), and the module waits for the fibers. Found with
  bench/parallel.bjo; the same code from ~main~ or a benchmark body works.
  It should be an error, or the fibers should not wait.
- ~array->column~ is generic over any ~%a~, so an array of strings
  compiles and is then an exception of Arrow at run time: Bjolang's string
  is a struct, which meets ~where T : struct~, but holds a reference, which
  Arrow's buffers cannot. Strings go to ~array->string-column~. A
  constraint on ~array->column~ of the types Arrow stores would make it a
  Bjolang error.
- A number that only ~summing~ uses is an ~int~, as Bjolang reads a literal,
  so ~(:acc (summing x))~ over cells asks for a column of ints, and a column
  of doubles is an Err at run time. Such a value needs its type written.
