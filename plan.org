* bjostat: the plan

What is done, and what comes next. The design is in three layers, as in Polars
and Spark: a table whose schema is known when the program runs, a query that
is checked against that schema before it runs, and typed views where a
program wants static types.

** Done: tables (bjostat table)

- A ~Table~ is an Arrow ~RecordBatch~. Its schema is read at run time.
- A column is taken out by name and type, and the type is checked once:
  ~(doubles t "price")~ is a ~(Column double)~ or an ~Err~ that names the
  columns the table has.
- A typed column gives its values as a span. The aggregates use
  ~TensorPrimitives~ when the column has no nulls.
- Arrow IPC files in and out. A file of several batches is read as one
  table, each column in one piece.

** Done: CSV (bjostat csv)

- ~read-csv~ and ~csv->table~ read through ~(text csv)~. The types are
  guessed from the first rows, or given by name with ~#:types~. An empty
  field is a null.
- The glue parses each field from its UTF-8 bytes into arrays from the
  shared pools, and makes Arrow buffers once. 1 000 000 rows of five columns
  in 175 ms; ~(text csv)~ alone takes 95 ms.
- Faster still would be fields as spans of the reader's chunk: ~(text csv)~
  now makes a string of each field and an array of each row, which is most
  of what it allocates, and read-csv only copies the bytes on.
- Not yet: other null markers such as ~NA~, booleans, dates, and columns
  that are skipped.

** Done: the function layer of queries (bjostat query)

- ~(column-as t name)~ gives ~(Cells %a)~ at the type its use gives; the
  check of the Arrow type against ~%a~ is in the glue, by ~typeof(T)~.
- A row spec is ~col~ and ~both~, as the applicative of Laurent Mazare's
  OCaml ~dataframe~: ~(both (col "price") (col "qty"))~ is a
  ~(Row (Tuple double long))~, checked against the schema before a row is
  read.
- ~where-rows~, ~count-rows~ and ~create-column~ take a spec and a
  function. Nulls are as in SQL. ~where-rows~ gathers the rows kept in the
  glue: fixed-width types by their width, strings, booleans, and runs of
  slices for the rest.

Measured on 1 000 000 rows, two columns read (bench/query.bjo):

| Loop                          | Time        | Against spans |
|-------------------------------+-------------+---------------|
| over the spans, by hand       | 0.38–0.50 ms | 1             |
| over cells, by hand           | 0.75–1.3 ms | 2–3           |
| ~count-rows~: closures, tuple | 5.8–6.7 ms  | 12–15         |
| ~where-rows~: count and gather | 7.4–8.9 ms |               |

So the macros write the loop over cells themselves, with the body in it,
and the function layer is for names known only at run time. A cell read
first made a span of the buffer each time; Arrow's own buffers are native
memory, so cells now pin them once and read through a pointer (1.8 to
1.3 ms in one run). A struct for cells gained nothing.

Cells are ~Iterable~, with an ~(Option %a)~ for each row, so a ~loop~ walks
columns side by side and the SQL rule is ~:when-let~:

#+BEGIN_SRC scheme
(loop (:for p* price) (:for q* qty)
      (:when-let (Some p) p*) (:when-let (Some q) q*)
      (:when (and (> p 250.0) (> q 20L)))
      (:acc (counting p)))
#+END_SRC

That loop takes 1.51 ms where the loop over cells by hand takes 1.44 ms, in
one run: an Option is a struct, and the null costs about 5%. So the macros
expand to this loop form, and a program can write it too. ~skip-nulls~ walks
only the values, as Julia's ~skipmissing~, for one column on its own.

** Done: collectors, for loops over cells

The columns are found before the loop, with ~column-as~ in a ~def~ where an
~Err~ can propagate, and the loop does the rest. There is no query form of
its own: ~where~ is a ~:when~, ~create~ a ~:let~, and ~aggregate~ an ~:acc~,
so a pipeline is one loop and makes no table between its steps.

- ~(selecting t row)~: the table of the rows kept. 4.4 ms on 1 000 000 rows,
  against 8.6 ms for ~where-rows~.
- ~(column-building x)~ and ~(column-building/option o)~: a column, with a
  null at each ~None~; ~table-with~ adds it. 3.5 ms; the arrays come from the
  shared pool, as in the CSV reader, and before that it took 13.4 ms.
- ~(grouping c (Tuple key x))~: a map from each key to what the collector
  ~c~ makes of its values. ~(pairing c d)~ is two collectors at once, so
  ~(grouping (pairing summing counting) ...)~ gives two aggregates of each
  group. ~map->table~ makes a table of a map. A collector over a collector
  needed nothing new in Bjolang: the implementation names the associated
  types of the inner one, as ~(assoc Collector acc %c)~.

~grouping~ is slow yet: 52 ms by four string keys, 12 ms by forty long
keys. A string key is copied out of Arrow and hashed at each row; the long
keys allocate 30 bytes a row, maybe the inner collector's values boxed
through its dictionary. To do: codes for the strings of a column, found
once, so that a group is found by an int; and a look at what the long keys
allocate.

A number that only ~summing~ uses is an ~int~, as Bjolang reads a literal,
so the column is asked for as ints, and a column of doubles is an ~Err~ at
run time. Such a value needs its type written.

Found in the Bjolang compiler:
- A column type that nothing decides is left as ~object~, and C# then
  refuses the call of ~col~. It should be a Bjolang error that asks for the
  type.
- The inferred ~where~ clauses are on functions only, not on type
  declarations: a Bjolang struct holding a ~Cells<T>~ with ~where T : struct~
  is refused by C#. The glue's ~Cells<T>~ has no constraint for that reason.

** Next: queries, checked before they run

A query is a value, a plan, not a series of calls:

#+BEGIN_SRC scheme
(query sales
  (where (> price 10.0))
  (group-by region)
  (summarise (total (sum price)) (n (count))))
#+END_SRC

- *The plan is checked against the table's schema before any row is read.*
  Each step gives the schema it makes from the one it gets, so a misspelt
  column or a type that does not fit is an error about the query, at once:
  "~price~ is a column of string, and ~sum~ takes a number". This is what
  ~LazyFrame.collect_schema()~ is in Polars, and it is what makes a table
  whose schema is dynamic safe to work with.
- *The query is a macro.* It reads the expressions when the program
  compiles, so ~(> price 10.0)~ becomes a loop over the column's span, with
  no interpreter between. The column's type is found when the plan is
  checked, so the macro makes the loop for each type it can be.
- *Steps:* ~where~, ~select~, ~mutate~ (new columns), ~group-by~ with
  ~summarise~, ~order-by~, ~limit~, ~join~. ~where~ makes a selection vector,
  not a copy, and the next step reads through it.
- *The order of work:* ~where~ and ~select~ with plan checking, then the
  aggregates with ~group-by~ (a hash table on the keys), then ~order-by~ and
  ~join~.

** Later

- *Typed views.* A macro over a record type that checks a table's schema
  once and makes typed accessors: ~Dataset[T]~ in Spark.
- *DuckDB* for joins, windows and Parquet, with Arrow between it and the
  tables, so a query too large or too relational for the kernels here goes
  there.
- *Parquet* into tables.
- *Chunked columns.* A table is one record batch now, and reading a file of
  many batches copies each column into one. A column of many chunks keeps
  them, for files larger than memory and for streams.
- *More types:* booleans, timestamps and dates, decimals, dictionaries.
- *Notebooks.* A Jupyter kernel over Bjolang's REPL, with tables shown as
  HTML and plots as Vega-Lite.

** Found in Bjolang while writing this

Both are fixed in Bjolang, and the generic code is now in Bjolang, not in
the glue.

- A generic ~import/extern~ did not take Bjolang's ~string~ for a .NET
  ~System.String~ parameter. Now it does, and the call converts it.
- A Bjolang function generic over ~(Column %a)~ was a C# method generic over
  ~T~ without Arrow's constraint ~where T : struct~, which C# refused. Now
  Bjolang finds the constraints and writes them as ~where~ clauses. A call at
  a type that breaks one is a Bjolang type error.
